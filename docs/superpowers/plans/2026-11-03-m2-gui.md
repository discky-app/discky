# Milestone 2: Discky.app (GPUI GUI + robo-duck) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship `Discky.app`: the Overview screen, category views with inspector, the removal dialog with live step statuses, Settings, the robo-duck scan animation and app icon, bundled and signed, on top of the Milestone 1 core.

**Architecture:** A new crate `discky-app` (GPUI via `gpui-kit`) holds one `Arc<Engine>` in a global and renders a Codex-like shell: hidden title bar, 212 px sidebar, content area, optional 400 px inspector. Before the GUI, four core tasks close the Milestone 1 follow-ups the GUI depends on: engine options instead of env reads, scan events + cancel, per-step execution events + admin-privileged removal, snapshot reload. A small `xtask` crate renders the pixel-art icon and assembles/signs the bundle.

**Tech Stack:** Rust 1.99 (edition 2024), `gpui-kit = "=0.9.0"` (pins `gpui-pre 0.3.11`, Metal), `smol = "2"` for channels, `png` for icon rendering in xtask, `codesign`/`iconutil` from macOS.

**Spec:** `docs/superpowers/specs/2026-11-02-discky-design.md` (§3, §4, §7, §11, §11a, §12b, §12c, §13, §14, §17). Follow-ups list: `docs/superpowers/plans/2026-11-03-m1-followups.md` (section "Must land with the GUI").

## Global Constraints

- UI copy, code comments, rule texts: **English** (spec §12a). No localization layer.
- Only official removal mechanisms; on a failed step the plan stops; never fall back to `rm` (spec §7). The GUI runs plans with `allow_interactive = true`; the MCP server stays at `false`.
- Removal mode setting "Trash / Permanent" applies only to Trash/Remove steps, never to tool commands (spec §7). "Show commands before running" cannot be turned off (spec §17.6).
- Dependencies: `gpui-kit = "=0.9.0"` only; **never** depend on `gpui`, `gpui-pre` or `gpui-component` directly (spec §3). Import GPUI with `use gpui_kit::*;` and components from `gpui_kit::component::*`. Use `gpui_kit::actions!`, not GPUI's macro.
- Colors come from `cx.theme()` semantic fields (`background`, `foreground`, `muted_foreground`, `border`, `sidebar`, `primary`, `danger`, `warning`, `success`); no raw hex/rgb in views. Exception: the duck sprite palette in `duck/sprites.rs`.
- Layout numbers (spec §11): window 1100×720 (min 800×500), sidebar 212 px, inspector 400 px, title bar 34 px, traffic lights at (9, 9).
- Sizes shown decimal like Finder: 1 GB = 1 000 000 000 bytes, one decimal below 10 ("9.1 GB", "14 GB", "527 MB"). Default column = `allocated`; "Frees" column = `freed_if_deleted` (spec §17.1).
- UI never blocks on the engine: scans, planning (`Engine::plan` stats paths) and execution run off the main thread; progress reaches the UI at most every 100 ms (spec §14).
- Minimum macOS 15 (`LSMinimumSystemVersion = 15.0`, `MACOSX_DEPLOYMENT_TARGET=15.0`); Apple Silicon only is fine.
- No new env-var reads in the app; the core keeps `HOME` and `OLLAMA_HOST` (ruling, see Task 1).
- `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` green after every task. Commit after each task.
- The GPUI dependency graph builds for minutes: run `cargo build -p discky-app` once early in each app task and reuse the target dir; never `cargo clean`.

## Review Focus

Spec-implied inputs no task's tests fully exercise; each has a pinning test in the task named.

1. **First launch: no snapshot, no Full Disk Access.** Overview shows an empty state with a "Scan now" button and the app never panics; the first scan then shows `no_access` count honestly. → Task 6 (`overview_model_without_snapshot`), Task 12 (`fda_status_from_errors`).
2. **A scan shorter than 1.5 s** (one small root) must not flash the duck scene; the scene only starts after 1.5 s of scanning (spec §11a). → Task 8 (`scene_hidden_before_grace_period`).
3. **The plan goes stale between opening the dialog and pressing Run** (another process removed a file). The dialog says what changed and offers "Re-plan"; nothing executes. → Task 11 (`stale_error_maps_to_replan`), core test already in `tests/execute.rs`.
4. **`config.toml` is malformed at launch.** The app opens a dialog naming the file and the parse error with "Reset to defaults" and "Quit"; it never exits silently. → Task 5 (`startup_error_text_names_file`).
5. **Selection must follow the finding, not the row**: re-sorting, filtering (⌘F) and a rescan must keep/clear selection by `FindingId`, and `DoNotTouch` rows can never be selected. → Task 9 (`selection_survives_sort_and_filter`, `do_not_touch_is_not_selectable`).

### Task 3: Per-step execution events and privileged removal

**Files:**
- Modify: `crates/discky-core/src/plan/execute.rs`, `crates/discky-core/src/engine.rs`
- Test: `crates/discky-core/tests/execute.rs`, unit tests in `execute.rs`

**Interfaces:**
- Produces:
  ```rust
  #[derive(Debug, Clone)] pub enum StepEvent { Started { index: usize }, Finished(StepResult) }
  // ExecuteOptions gains `pub on_step: Option<StepSink>`; `ExecuteRequest.on_step` (Task 1) is forwarded.
  pub(crate) fn finder_delete_script(paths: &[PathBuf]) -> String;
  pub(crate) fn admin_rm_script(paths: &[PathBuf]) -> String;
  ```
- Behaviour (spec §7, follow-ups "Interactive steps are unimplemented"):
  - `StepKind::Trash` with `INTERACTIVE` and `allow_interactive = true` → `osascript -e <finder_delete_script>` where the script is `tell application "Finder" to delete {POSIX file "<p1>", POSIX file "<p2>"}`; AppleScript string escaping: `\` → `\\`, `"` → `\"`. Finder prompts for an administrator password itself for root-owned items. Then the usual `verify_gone`.
  - `StepKind::Remove` with `INTERACTIVE` and `allow_interactive = true` → `osascript -e <admin_rm_script>` = `do shell script "/bin/rm -rf <q1> <q2>" with administrator privileges`, where each path is POSIX-single-quoted (`'` → `'\''`) **and then** AppleScript-escaped. Then `verify_gone`.
  - Non-interactive Trash/Remove steps are unchanged. `Started` fires before each selected step runs; `Finished` after its `StepResult` is final (after the history write).
