# Discky — дизайн-документ

Дата: 2026-11-02. Статус: прошёл проверку ревьюером-строителем, ждёт одобрения владельца.

Макеты, на которые ссылается документ, лежат в `.superpowers/brainstorm/47903-1793645957/content/` (файлы `01-main-screen.html` … `05-settings-mcp.html`). Они иллюстрируют компоновку и тон, не пиксели.

## 1. Зачем

Личная утилита для одного Mac (Apple Silicon, macOS 26), чтобы держать диск чистым. Боль владельца не «диск заполнен», а «не понимаю, кто и чем его забил»: модели, которые приложения ставят за спиной; кэши и сборки dev-инструментов; хвосты удалённых приложений; версии языков, которые никто не использует. Существующие инструменты показывают либо дерево папок без смысла (GrandPerspective, Diskscape), либо чистят «по-своему», минуя официальные механизмы.

Discky отвечает на два вопроса: **«что можно освободить и почему это безопасно»** и **«как удалить это правильно»**, где «правильно» значит через официальный путь инструмента или системы (`brew uninstall --zap`, `mise uninstall`, `ollama rm`, `/usr/bin/trash`, `pkgutil`, `launchctl bootout`), а не `rm -rf` по догадке.

Третье требование, добавленное в ходе обсуждения: то же ядро доступно агенту через **MCP-сервер по stdio**, чтобы чистить диск можно было разговором из Claude Code / Codex / Cursor.

## 2. Цели, не-цели, анти-цели

**Цели**

1. За ~20 секунд после запуска показать обзор: сколько занято, сколько можно освободить безопасно, топ-находки по категориям.
2. Честные байты везде: реально выделенное на диске, а не заявленный размер. OrbStack/Docker sparse-образы показываются как 11 ГБ, а не 460.
3. Для каждой находки: откуда она, регенерируется ли, какой командой удаляется.
4. Деинсталляция приложений с хвостами, с определением источника (cask / pkg / App Store / перетащено).
5. Управление версиями языков через mise: что стоит, кто запрашивает, что лишнее.
6. Treemap диска как второй режим, на том же индексе.
7. MCP-сервер с теми же возможностями, безопасный по умолчанию.
8. Чистый Rust, GPUI, внешне в духе десктопного Codex: тёмный, узкий сайдбар, спокойная типографика.

**Не-цели (в первой версии)**

- Другие менеджеры версий (nvm, rbenv, pyenv, asdf). Добавляются через issue на GitHub.
- Фоновый индекс и слежение за файловой системой. Скан только по запросу.
- App Store, sandbox, подпись для широкой публики. Распространение через Homebrew cask.
- Дубликаты файлов, очистка памяти, «ускорение мака» и прочий CleanMyMac-фольклор.
- Windows/Linux.

**Анти-цели (что сделает проект провалом, даже если всё работает)**

- Удалить то, что пользователь не выбирал, или удалить способом, который инструмент не поддерживает.
- Молча пропустить папку без доступа или молча сделать `rm`, когда официальная команда упала.
- Соврать в цифрах: посчитать sparse-файл по заявленному размеру, посчитать жёсткую ссылку дважды, скачать iCloud-заглушку при сканировании.
- Превратиться в «дашборд»: пёстрые графики вместо списка с кнопкой.

## 3. Ограничения

- Один пользователь, один Mac: alxgol, macOS 26.2, Apple Silicon. Нет необходимости поддерживать Intel или старые macOS; минимум — macOS 15 (см. §13).
- Не sandbox. Приложение запускается как обычный пользователь. Операции, требующие root (LaunchDaemons, `/Library`), идут через `sudo` с системным запросом пароля (osascript `with administrator privileges` или `sudo -A`), и такие шаги помечаются заранее.
- Full Disk Access нельзя запросить программно. Приложение детектирует отказ (EPERM на `~/Library/Mail`, `~/Library/Safari`), показывает статус в Настройках → Доступ к диску и даёт кнопку, открывающую нужную панель System Settings.
- Чтение чужих `~/Library/Containers/*` вызывает системный запрос «доступ к данным других приложений». Это нормально, один раз на запуск процесса.
- GPUI вне Zed молодой. Берём `gpui-kit` (бывший gpui-component), который пинит `gpui-pre`. Никаких прямых зависимостей на upstream `gpui`, чтобы не ловить несовпадение типов.

## 4. Архитектура

Один Cargo workspace, три крейта:

```
discky/
  crates/
    discky-core/   библиотека: скан, индекс, категории, правила, планировщик удаления, адаптеры инструментов
    discky-app/    GPUI-приложение, бинарник Discky.app
    discky-mcp/    stdio MCP-сервер, бинарник discky-mcp
```

`discky-core` не знает ни про GPUI, ни про MCP. Оба фасада вызывают одно и то же API: `scan()`, `findings(category, filter)`, `inspect(id)`, `plan_removal(ids)`, `execute_plan(plan_id)`, `history()`. Любая новая возможность сначала появляется в core и автоматически доступна обоим фасадам.

Индекс живёт в памяти процесса. После скана снимок сохраняется в `~/Library/Application Support/Discky/snapshot.bin` (бинарная сериализация, формат — на усмотрение строителя), чтобы следующий запуск начинал с прошлой картины с пометкой «данные от 2 ноября 21:40, пересканировать?».

Настройки — TOML в `~/Library/Application Support/Discky/config.toml`, общий для app и mcp. Лог удалений — `~/Library/Logs/Discky/removals.log`, append-only JSON lines.

## 5. Сканер и честные байты

**Обход.** Параллельный обход по директориям (пул потоков, очередь директорий, как в jwalk), внутри каждой директории — `getattrlistbulk(2)` с запросом: `ATTR_CMN_NAME`, `ATTR_CMN_RETURNED_ATTRS`, `ATTR_CMN_OBJTYPE`, `ATTR_CMN_FLAGS`, `ATTR_CMN_MODTIME`, `ATTR_CMN_ACCTIME`, `ATTR_CMN_FILEID`, `ATTR_FILE_LINKCOUNT`, `ATTR_FILE_DATAALLOCSIZE`, `ATTR_FILE_DATALENGTH`, `ATTR_CMNEXT_PRIVATESIZE`, `ATTR_CMNEXT_CLONEID`, `ATTR_CMNEXT_EXT_FLAGS`. Один syscall на десятки записей вместо readdir + lstat на каждую. Ориентир производительности: ~200 000 файлов/с, домашняя папка в 4 млн файлов — около 20 секунд.

**Размеры.** Для каждого файла храним три числа:
- `allocated` — `DATAALLOCSIZE`, реально выделенные блоки. **Это размер по умолчанию во всех экранах.**
- `logical` — `DATALENGTH`, заявленный размер. Показывается по переключателю «Заявлено».
- `freed_if_deleted` — `PRIVATESIZE`: сколько реально освободится при удалении с учётом клонов APFS и снапшотов. Именно это число стоит в колонке «Освободится» и в итогах плана удаления.

Если `PRIVATESIZE` не вернулся (не APFS, сетевой том), `freed_if_deleted = allocated`.

**Жёсткие ссылки.** Файл с `LINKCOUNT > 1` считается один раз по `FILEID` в пределах тома. Остальные вхождения показываются с размером 0 и пометкой «жёсткая ссылка».

**Dataless (iCloud-заглушки).** Файлы с `SF_DATALESS` в флагах не открываются и не читаются (иначе macOS их скачает). В дереве они отображаются пунктиром с заявленным размером и подписью «в облаке, не на диске», в итоги не входят. Перед сканом процесс выставляет `setiopolicy_np(IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES, …, OFF)`.

**Sparse.** Файл, у которого `allocated` меньше `logical` более чем на 10 % и больше 1 ГБ разницы, помечается `sparse`. Известные случаи: OrbStack `data.img.raw`, Docker `Docker.raw`, образы симуляторов.

**Недоступные папки.** EPERM/EACCES не пропускаются молча: узел помечается «нет доступа», список таких узлов виден в Настройках → Доступ к диску и в сводке скана.

**Границы.** Скан не пересекает точки монтирования и не заходит в `/System`, `/private/var/vm`, `/Volumes/*`. По умолчанию корни: `~` и `/Applications`; плюс `/Library` и `/usr/local`, `/opt/homebrew` для dev-кэшей. Список корней редактируется в Настройках → Сканирование. Пользовательские исключения (glob) там же.

## 6. Категории и правила

Категория назначается узлу правилом. Правило — это: шаблон пути (или bundle id, или маркер вроде «папка содержит `Cargo.toml` рядом с `target/`»), категория, метка безопасности, официальная команда удаления (если есть), текст «что это и регенерируется ли». Правила лежат в core как данные (TOML-файл, встроенный в бинарник), а не как код, чтобы их было легко дополнять.

Категории сайдбара (порядок = порядок в UI):

| Категория | Что попадает | Откуда правила |
|---|---|---|
| **Приложения** | `.app` в `/Applications`, `~/Applications`; с датой запуска, источником и суммой «приложение + хвосты». Подрежим «остатки удалённых»: хвосты, чей bundle id не соответствует ни одному установленному приложению | Spotlight (`kMDItemLastUsedDate`, fallback — mtime кэшей приложения), Caskroom, `pkgutil --file-info`, `_MASReceipt` |
| **Кэши приложений** | `~/Library/Caches/*`, `~/Library/Application Support/*`, `~/Library/Group Containers/*`, `~/Library/Containers/*`, сгруппированные по приложению-владельцу | bundle id из имени папки; zap-stanza Homebrew для известных касков; встроенная таблица известных тяжёлых мест (Claude `vm_bundles`, Chrome, DriveFS, Telegram, WhatsApp, MacWhisper `models`, VSCode `ShipIt`, …) |
| **Модели** | ollama (`~/.ollama/models`, список через `GET /api/tags`), HuggingFace hub (`~/.cache/huggingface/hub`), oMLX (`~/.omlx/models`), LM Studio (`~/.lmstudio/models`), модели внутри приложений (MacWhisper, gliner и т.п. по таблице) | по путям; имена моделей — из API/манифестов, не из имён blob-файлов |
| **Dev-кэши** | cargo registry/git, rustup toolchains, npm/pnpm/yarn/bun, pip/uv, Go modcache, gem, CocoaPods, SwiftPM, Gradle, Xcode DerivedData / DeviceSupport / Archives, CoreSimulator, Docker/OrbStack образы, Homebrew cache, Playwright browsers | таблица путей + официальная команда очистки на каждый |
| **Сборки проектов** | `target/`, `node_modules/`, `.venv/`, `build/`, `dist/`, `.next/`, `.gradle/` внутри папок с маркером проекта (`Cargo.toml`, `package.json`, `pyproject.toml`, …). Исключаются такие же папки внутри `~/Library`, `~/.vscode/extensions` и т.п. | маркер проекта + дата последнего изменения исходников проекта (не самой сборки) |
| **Версии языков** | установки mise: `mise ls --json` + `mise ls --all-sources` | §9 |
| **Большое и старое** | файлы > 500 МБ или папки, не менявшиеся > 1 года, вне предыдущих категорий; Загрузки отдельной группой | эвристика по размеру/возрасту; пороги в Настройках |

**Гранулярность находок.** Где владелец назвал предмет — находка на предмет: модели (каждая модель отдельно, имя из API/манифеста), версии mise, приложения. Dev-кэши в первой версии — **одна находка на кэш** с одной официальной командой (`cargo cache --autoclean`, `uv cache clean`, `xcrun simctl delete unavailable`, `docker system prune`, …), без per-item адаптеров (`rustup toolchain uninstall`, `simctl delete <udid>`, `docker rmi`); внутренности кэша видны через карту и `tree`. Per-item для dev-кэшей — кандидат на вторую версию по запросу.

Docker/OrbStack особый случай: на хосте это один sparse-файл. Находка показывает `allocated` хоста; шаг `docker system prune` в колонке «Освободится» пишет «до N ГБ внутри VM, хост-файл сожмётся позже» с числом из `docker system df` (reclaimable), а в итог плана не суммируется.

Метки безопасности (одна на находку, показывается цветом и словом):
- **регенерируется** — кэш/сборка, восстановится само (зелёная);
- **данные приложения** — удаление возможно, но приложение потеряет состояние (серая, без галочки по умолчанию);
- **нужен пароль** — шаг требует администратора (жёлтая);
- **приложение запущено** — сначала закроем (жёлтая);
- **не трогаем** — Keychain, системные папки, данные без правила (без галочки, недоступна для выбора по умолчанию).

Узел без правила в категорию не попадает, он виден только в карте диска. Это осознанно: категории — это то, про что мы можем объяснить «почему безопасно».

## 7. Удаление: план и выполнение

Удаление всегда двухфазное.

**План** (`plan_removal`): на вход — список id находок (или путей), на выход — упорядоченный список шагов. Шаг: описание человеческим языком, команда (или «в Корзину: путь»), ожидаемо освободится, предупреждения. План имеет id, время создания и отпечаток состояния (mtime/размер затрагиваемых путей). Побочных эффектов нет.

Порядок шагов внутри плана: закрыть приложение → выгрузить агенты/демоны → официальная команда инструмента → наши удаления файлов → `defaults delete` → `pkgutil --forget`. Если официальная команда не найдена (инструмент не установлен) или завершилась с ошибкой, **план останавливается на этом шаге**, остальные шаги не выполняются, пользователю показывается вывод команды (см. поправку 2026-11-04 в §13). Никакого «ну тогда rm».

**Выполнение** (`execute_plan`): проверяет отпечаток (изменилось — отказ, «перепланируй»), выполняет шаги по порядку, пишет каждый в лог с выводом команды. В GUI это лист с живыми статусами (макет `02-uninstall.html`, вариант 2). По завершении: тост «освобождено X», и если что-то ушло в Корзину — «Y в Корзине» с кнопкой очистить.

**Способ удаления файлов** — настройка «В Корзину / Навсегда»:
- В Корзину (по умолчанию): `/usr/bin/trash` (macOS 15+). Файлы, принадлежащие root, идут через Finder (osascript) с системным запросом прав.
- Навсегда: `rm -rf` нашими руками, только для путей, которые мы сами нашли по правилу. Пользователь предупреждён в настройке.
- Настройка **не** применяется к шагам, которые выполняет инструмент (`brew uninstall --zap`, `mise uninstall`, `ollama rm`, `cargo clean`, `docker system prune`, `hf cache rm`, `xcrun simctl delete unavailable`, `uv cache clean`, …): они удаляют по-своему.

«Показывать команды перед выполнением» всегда включено, выключить нельзя.

## 8. Деинсталляция приложений

Для каждого `.app` определяем источник, по убыванию приоритета:

1. **Homebrew cask**: в `$(brew --caskroom)/<token>/<ver>/` есть симлинк на этот `.app`. Хвосты и порядок — из `brew info --cask --json=v2 <token>` (`uninstall` + `zap` stanza). Удаление: `brew uninstall --zap <token>`.
2. **.pkg**: `pkgutil --file-info-plist <путь к .app>` возвращает `pkgid`. Список файлов — `pkgutil --files <pkgid>`. Удаление: в Корзину файлы из списка (кроме системных путей), затем `pkgutil --forget <pkgid>`.
3. **App Store**: есть `Contents/_MASReceipt/receipt`. Удаление: в Корзину.
4. **Перетащено**: всё остальное. Удаление: в Корзину.

Независимо от источника ищем хвосты по bundle id (`CFBundleIdentifier` из `Info.plist`) и по имени приложения в: `~/Library/{Application Support, Caches, Preferences, Containers, Group Containers, Saved Application State, HTTPStorages, WebKit, Cookies, Logs, LaunchAgents, Application Scripts}`, `/Library/{LaunchAgents, LaunchDaemons, Application Support, PrivilegedHelperTools, Preferences}`. Настройки удаляются через `defaults delete <domain>`, а не `rm` plist. LaunchAgents/Daemons сначала `launchctl bootout`, потом в Корзину. Keychain-записи показываем, но по умолчанию не трогаем.

Если у приложения есть собственный деинсталлятор (`Uninstall*.app` рядом, или `uninstall` script в cask), он идёт первым шагом плана.

`/System/Applications/*` и всё с флагом `restricted` в список не попадает.

Дата последнего запуска: `kMDItemLastUsedDate`; если Spotlight не знает (у владельца так у 19 из 47 приложений), берём максимум mtime по хвостам приложения и показываем со звёздочкой «оценка».

«Остатки удалённых»: хвосты в перечисленных папках, bundle id которых не соответствует ни одному установленному приложению и ни одному запущенному процессу/агенту. Метка — «данные приложения», с указанием имени, если удалось восстановить из bundle id.

Уточнение (веха 3): «установленное приложение» = bundle id известен LaunchServices/Spotlight; без Spotlight остатки показываются без галочек.

## 9. Версии языков (mise)

Источник данных — только CLI mise, без чтения его внутренних файлов:
- `mise ls --json` — установленные версии, пути, активность, запрошенная версия.
- `mise ls --all-sources` — какой конфиг какую версию запрашивает (глобальный `~/.config/mise/config.toml`, `mise.toml`, `.mise.toml`, `.tool-versions` в проектах).
- `mise prune -n` — что mise сам считает лишним; показывается кнопкой «mise prune (dry-run)».

Статусы: **глобальная** / **закреплена в N проектах** (список файлов в инспекторе) / **не используется**. Legacy-файлы (`.nvmrc`, `.node-version`, `.ruby-version`, `.python-version`) mise читает, только если включены в его настройках; мы их находим в тех же проектах при скане и показываем отдельной строкой с пометкой «legacy, в mise выключено», чтобы пользователь не удалил версию, на которую рассчитывает старый проект.

Удаление — только `mise uninstall <tool>@<version>`. Глобальную версию удалить нельзя, пока она глобальная.

В Настройках → Менеджер версий единственный вариант: mise. Текст: «Нужен другой (nvm, rbenv, pyenv, asdf)? Открой issue на GitHub». Никаких «скоро».

## 10. Карта диска

Отдельный пункт сайдбара, на том же индексе. Squarified treemap, рисуется одним `canvas` в GPUI с ручной геометрией и собственным hit-testing (как в disktree): тысячи прямоугольников, hover через поиск плитки под курсором, без hitbox на каждую.

Тулбар: хлебные крошки пути; переключатель раскраски «Категория / Возраст / Файлов»; «На диске / Заявлено»; глубина отрисовки (1–4). Плитки окрашены по категории содержимого; sparse-файлы с рамкой и подписью; dataless — пунктиром. Клик по плитке открывает **тот же инспектор справа**, что и в категориях (путь, размеры, дата, владелец-приложение, правило, кнопки «Открыть в Finder», «В Корзину», «→ в категорию» если это известная находка). Двойной клик — спуск внутрь. Наведение — короткий тултип.

*Поправка 2026-11-04.* Dataless-файлы (iCloud) весят 0 на диске, поэтому карта показывает их только в режиме «Заявлено» (пунктиром, подпись «in the cloud»); в «На диске» их нет, и в итоги они не входят. Раскраска «Категория» означает категорию находок Discky через ближайшую находку-предка (плюс «Не категоризовано» и «В облаке»); классы media/documents из макета не реализованы.

## 11. Интерфейс

Окно: скрытый заголовок с инсетом светофоров (как в Zed/Codex), сайдбар 212 px, основная область, опциональный инспектор справа 400 px, нижняя панель действий в видах категорий. Тёмная тема по умолчанию, следует системной. Шрифт системный.

Сайдбар: Обзор; группа «Находки» с семью категориями и их весом справа; группа «Диск» с Картой; внизу Настройки.

**Обзор** (стартовый экран, макет `01-main-screen.html` вариант A): крупная цифра «можно освободить безопасно» (сумма находок с меткой «регенерируется»), полоса диска по группам, карточки категорий с топ-4 и ссылкой «ещё N». Кнопка «Пересканировать» и время последнего скана в тулбаре.

**Вид категории** (макет `01-main-screen.html` вариант B как таблица + инспектор из `02-uninstall.html`): таблица с галочками, сортировка по размеру / давности / приложению, колонка «Освободится», нижняя панель «Выбрано N · X ГБ → способ» с кнопками «Показать в Finder» и «Удалить…». Клик по строке — инспектор справа.

**Инспектор**: заголовок, метаданные (bundle id, источник, версия), список составляющих с галочками (для приложения — хвосты; для версии mise — кто запрашивает; для папки — топ детей), блок «Что будет выполнено» с командами.

**Лист подтверждения**: шаги плана со статусами, предупреждения, «Отмена» / «Выполнить». После выполнения остаётся с результатами и ссылкой на лог.

**Настройки** (макет `05-settings-mcp.html`): Сканирование (корни, исключения, пороги «большого и старого»); Удаление (Корзина/навсегда, напоминание о Корзине, лог); Менеджер версий (mise); MCP-сервер (§12); Доступ к диску (статус FDA, список недоступных папок, кнопка в System Settings); О программе (версия, GitHub, место под ссылку на донат).

Меню macOS: стандартное (About, Settings ⌘,, Quit), плюс «Пересканировать ⌘R». Горячие клавиши в таблицах: пробел — галочка, ⌫ — «Удалить…», ⌘F — фильтр по имени.

## 11a. Робоутка: анимация скана и айдентика

Решение владельца, добавлено 2026-11-02 после одобрения документа; реализуется в вехе 2 (GUI).

**Логотип.** Пиксель-арт робоутки. Иконка приложения, иконка в тулбаре, favicon README.

**Анимация скана.** Пока идёт скан, вместо прогресс-бара на экране Обзора играет процедурная сцена: робоутка ходит, собирает бумажки и папочки и скидывает их в одну корзину. Сцена управляется событиями сканера, а не таймером:

- каждая новая порция файлов (прогресс-коллбек) — утка уходит за край экрана и возвращается с бумажками; размер стопки пропорционален количеству файлов в порции;
- когда сканер зашёл в большую папку (агрегат растёт долго в одном поддереве, порог настраивается, старт — 2 ГБ или 50 000 файлов), утка тащит один огромный блок на верёвке и с усилием запихивает его в корзину;
- сцена заканчивается ровно в момент завершения скана: утка ставит последнюю коробку, корзина закрывается, появляется цифра «можно освободить».

Технически: спрайтовая анимация на GPUI canvas (пиксель-арт, 2–4 кадра на состояние: идёт, несёт, тащит, кидает, стоит), состояния переключает конечный автомат, который читает `Progress` из ядра. Без видеофайлов, без зависимостей на медиа-библиотеки. Если скан короче 1.5 с — сцену не показываем, чтобы не мигала.

## 12. MCP-сервер

Бинарник `discky-mcp`, stdio, тот же `discky-core`. Устанавливается рядом с приложением (cask кладёт в `/opt/homebrew/bin`). В Настройках → MCP-сервер: путь к бинарнику и статус; тумблер «Разрешить агенту удалять» (**по умолчанию выключен**); вкладки с готовой строкой подключения для Claude Code (`claude mcp add discky -- /opt/homebrew/bin/discky-mcp`), Claude Desktop, Codex, Cursor и сырой JSON; кнопка «Скопировать»; список инструментов.

Инструменты (девять, намеренно без per-tool вариантов вроде `ollama_models`):

| Инструмент | Что делает | Побочные эффекты |
|---|---|---|
| `disk_overview` | том, занято/свободно/purgeable, суммы по группам, возраст снимка | нет |
| `scan` | запускает скан; см. асинхронность ниже | создаёт/обновляет индекс |
| `scan_status` | прогресс и итог по `scan_id` | нет |
| `findings` | находки категории: фильтры `min_size`, `older_than_days`, `label`, `sort`, `limit`, `cursor`; каждая со стабильным `id`, `allocated`, `freed_if_deleted`, датой, меткой безопасности, кратким правилом | нет |
| `tree` | топ-N детей пути по честному размеру | нет |
| `search` | поиск по индексу: glob/подстрока имени, размер, возраст, тип, категория | нет |
| `inspect` | один объект по id/пути/имени приложения: всё, что видит инспектор в GUI, плюс текст правила | нет |
| `plan_removal` | список id/путей → шаги с командами, итог, предупреждения, `plan_id` | нет |
| `execute_plan` | `plan_id`, опционально подмножество шагов | **только при включённом тумблере**, иначе ошибка с объяснением |
| `history` | лог удалений, что лежит в Корзине и может быть возвращено | нет |

(Инструментов в таблице десять, считая `scan_status`; он нужен только клиентам без расширения Tasks.)

Стабильный `id` находки — хеш от (вид, канонический путь), чтобы переживать повторные сканы.

**Асинхронный скан.** Фонового индекса нет (дорого по ресурсам, решение владельца). `scan` всегда возвращается сразу:
- если клиент при `initialize` объявил `extensions["io.modelcontextprotocol/tasks"]`, возвращается дескриптор задачи, клиент опрашивает штатным `tasks/get`;
- иначе возвращается `{scan_id, status: "running"}`, агент опрашивает `scan_status`;
- если клиент передал `progressToken`, сервер шлёт `notifications/progress` («1.2 млн файлов, ~Library/Caches»);
- параметр `wait_seconds` (0–60): подождать и вернуть итог сразу, если скан успел.

Снимок индекса на диске общий с приложением, поэтому агент после запуска сразу видит последнюю картину и дату.

Ресурсы MCP: `discky://snapshot/summary` (сводка последнего скана), `discky://config` (настройки, только чтение), `discky://log/removals`.

## 12a. Язык

Интерфейс, тексты правил, описания MCP-инструментов и документация — **на английском** (решение владельца: публичный tap, issues, агенты). Макеты на русском только потому, что брейншторм шёл по-русски. Слой локализации не делаем.

## 12b. Два процесса, один индекс

Discky.app и discky-mcp — независимые процессы, оба держат свой индекс в памяти. Общие файлы: `snapshot.bin`, `config.toml`, `removals.log`.

- Снимок пишется атомарно (во временный файл + rename) под advisory-блокировкой; в заголовке — версия формата, время, корни скана, **идентичность процесса** (app / mcp) и список недоступных папок. Разные TCC-гранты у двух процессов дают разные «нет доступа», поэтому читатель снимка видит, кем он сделан, и UI показывает это рядом с датой.
- Приложение следит за изменением файла снимка (один `kqueue`/FSEvents-наблюдатель за одним файлом, не за диском) и предлагает перезагрузить картину, если её обновил MCP.
- План проверяет отпечаток затрагиваемых путей **в момент выполнения**, поэтому удаление из другого процесса приводит к честному «изменилось, перепланируй», а не к тихой ошибке.
- `history` читает общий лог, видит удаления обоих процессов.
- Бюджет памяти ≤ 1 ГБ на процесс; одновременная работа обоих допустима.

## 12c. Что агент может выполнять

Каждый шаг плана несёт флаги: `interactive` (нужен диалог администратора, закрытие приложения, Finder через osascript) и `permanent` (безвозвратное удаление). `execute_plan` из MCP:
- при выключенном тумблере — отказ на любой шаг;
- при включённом — выполняет шаги без флага `interactive`; шаги с `interactive` пропускает и возвращает их списком «выполни в Discky.app» с причиной;
- настройку «Навсегда» MCP уважает, но каждый `permanent`-шаг отмечен в ответе `plan_removal`, чтобы агент показал это пользователю.

## 13. Распространение

- `cargo-bundle` (или свой xtask) собирает `Discky.app` с `Info.plist`, иконкой, `LSMinimumSystemVersion`.
- Homebrew tap владельца с cask: ставит `Discky.app` в `/Applications` и симлинк `discky-mcp` в `/opt/homebrew/bin`. Zap-stanza нашего же каска перечисляет наши собственные хвосты.
- Подпись: **не ad-hoc**. Гранты Full Disk Access и «данные других приложений» привязаны к подписи, ad-hoc меняет cdhash на каждой сборке, и доступ пришлось бы выдавать заново после каждого обновления. xtask подписывает стабильным self-signed сертификатом из Keychain владельца (создаётся один раз скриптом); при появлении Apple Developer ID — `--sign --notarize` тем же xtask. Без нотаризации первый запуск требует снять quarantine, cask делает это при `--no-quarantine` (см. поправку 2026-11-04 ниже).
- Минимальная macOS — 15 (`LSMinimumSystemVersion`), потому что `/usr/bin/trash` появился в 15 и fallback на macOS 14 негде тестировать. Если `gpui-pre` требует выше, берём его минимум.
- Донат: позже, ссылка в «О программе».

**Поправка 2026-11-04 (подготовка к запуску).** Tap — `AlxGolubev/homebrew-discky`; cask использует `app` и `binary` на `discky-mcp` внутри бандла (`Contents/MacOS/discky-mcp`). Нотаризации нет (платного аккаунта нет); Homebrew ≥ 5 убрал `--no-quarantine`, поэтому cask снимает атрибут quarantine сам — в `postflight` через `xattr -dr com.apple.quarantine` на `Discky.app` — и говорит об этом в caveats, а команда установки обходится без флагов. Релиз — только Apple Silicon: раннеры `macos-15` у GitHub — arm64, cask объявляет `depends_on arch: :arm64`. Релиз подписывается импортированным сертификатом Apple Development; без него сборка подписывается ad-hoc, и ценой этого Full Disk Access приходится выдавать заново после обновления. Онбординг Full Disk Access на Обзоре расширяет §3 («показывает статус в настройках»): открывает нужную панель, показывает бандл в Finder и после выдачи доступа предлагает карточку перезапуска. Правило исполнителя из §7 уточнено: упавшая команда инструмента, Quit или собственный шаг удаления источника находки (бандл приложения, файлы установщика; внутренний флаг шага `SOURCE`) пропускает только остальные шаги своей находки, упавший шаг «в Корзину» для остаточного пути ничего не блокирует, очередь останавливается только при невозможности записать журнал.

## 14. Производительность

- Скан домашней папки (4 млн файлов): цель ≤ 25 с на Apple Silicon с SSD, холодный кэш. Измерять на машине владельца.
- Память индекса: ≤ 1 ГБ для 4 млн узлов. Хранить имена в арене, пути собирать по цепочке родителей, не хранить строку пути на узел.
- UI не блокируется сканом: скан в своих потоках, прогресс в UI раз в 100 мс.
- Treemap: перерисовка 60 fps при наведении на 5 000 видимых плитках.
- Холодный запуск приложения со снимком на диске: ≤ 1 с до первого кадра обзора.

## 15. Риски и как с ними жить

- **GPUI churn.** Пин на точные версии `gpui-kit`/`gpui-pre`, обновлять осознанно. Если какой-то контрол в Kit сырой (Tree, DataTable), допустимо собрать свой на примитивах.
- **Tasks в MCP не поддержан клиентами.** Поэтому `scan_id` + `scan_status` обязательны, Tasks — бонус.
- **Spotlight не знает дат запуска.** Оценка по mtime хвостов со звёздочкой, честно подписано.
- **TCC-запросы при чтении Containers.** Один раз на процесс, объяснено в Настройках → Доступ к диску.
- **Apple ужесточает FDA.** Следить, не ломать поведение «нет доступа = помечаем, не падаем».
- **Правила категорий устаревают.** Правила — данные, легко править; неизвестное не категоризируется, а не угадывается.

## 17. Решения, принятые мной (проверь при чтении)

1. Размер по умолчанию везде — реально выделенный (`allocated`), в колонке «Освободится» — `PRIVATESIZE`.
2. Тумблер «Разрешить агенту удалять» выключен по умолчанию.
3. Узлы без правила не попадают в категории, только в карту.
4. Keychain-записи приложения показываются, но не удаляются по умолчанию.
5. При ошибке официальной команды план останавливается, fallback на `rm` отсутствует (см. поправку 2026-11-04 в §13).
6. «Показывать команды перед выполнением» нельзя выключить.
7. Корни скана по умолчанию: `~`, `/Applications`, `/Library`, `/usr/local`, `/opt/homebrew`.
8. Дата запуска без данных Spotlight оценивается по хвостам и помечается звёздочкой.
9. Инструменты MCP — девять общих, без per-tool (`ollama_*`, `mise_*`); `scan_status` десятый, только как fallback.
10. Минимальная macOS — 15, без fallback для Корзины.
11. Два процесса независимы, снимок общий с блокировкой, версией и идентичностью писавшего; приложение следит только за файлом снимка (§12b).
12. Dev-кэши в v1 — одна находка на кэш с одной командой; per-item только для моделей, версий mise и приложений (§6).
13. Из MCP выполняются только неинтерактивные шаги; шаги с паролем/закрытием приложений/Finder возвращаются как «выполни в Discky.app» (§12c).
14. Подпись стабильным self-signed сертификатом вместо ad-hoc, чтобы FDA переживала пересборки (§13).

Решения владельца, добавленные после проверки ревьюером: язык — английский (§12a); порядок вех — ядро + MCP, GUI, деинсталлятор + mise, карта (§12d).
